# DTS schema 说明

本包采用“先定 schema，再抽取 XLSX”的方式。`schema.py` 是 PDF 方位规则的代码来源；包内的 `schema.json` 是该规则的可阅读快照。每次运行会先核验指定 PDF 的 SHA-256，再在输出目录重新生成 `schema.json`，然后才处理表格。PDF 不一致时不会沿用旧规则继续抽取。

## 图谱结构

```text
(VehicleType) -[:CONTAINS {location}]-> (Part:具体部件名)
                                              |
                                              | DTS_POSITION_RELATION
                                              | {relative_position, Gap, Flush, Ra, Rb,
                                              |  Alignment, Consistent, Radii,
                                              |  classification, area}
                                              v
                                         (Part:具体部件名)
```

四张工作表各对应一个车型节点：`硬派越野车`、`城市SUV`、`豪华轿车`、`豪华SUV`。车型间不建立关系，同名部件也不会跨车型复用节点。

| 元素 | Label / 类型 | 保留的属性 | 含义 |
| --- | --- | --- | --- |
| 车型节点 | `VehicleType` | `id`, `name` | `id` 由工作表编号确定；`name` 是车型名称。 |
| 零件节点 | `Part` + Excel 中的具体部件名作为第二个 label | `id`, `name`, `location` | 例如 `:Part:散热器罩左饰板`；PDF 的泛化类别“饰板”不替代具体名称。 |
| 包含关系 | `CONTAINS` | `location` | 车型包含一个具有确定安装位置的零件实例。 |
| DTS 位置关系 | `DTS_POSITION_RELATION` | `relative_position`, `Gap`, `Flush`, `Ra`, `Rb`, `Alignment`, `Consistent`, `Radii`, `classification`, `area` | 连接两个具体零件实例；关系有方向。 |

`id` 是节点的技术标识，关系没有技术 ID。零件节点的身份由**车型 + 具体名称 + 稳定物理安装位置**共同确定：同一车型的“侧围”若确有左、右两个实例，就建两个节点；同一实例参与多个 DTS 要求时则复用一个节点。`Part.location` 与相应的 `CONTAINS.location` 一致。

`Part.location` 只允许以下 11 个值：`前部中央`、`前部左侧`、`前部右侧`、`后部中央`、`后部左侧`、`后部右侧`、`侧部左侧`、`侧部右侧`、`顶部中央`、`顶部左侧`、`顶部右侧`。它描述零件安装位置；`area` 是表格中 DTS 要求所属的区域（如“前部区域”），两者不能混用。

## PDF 方位规则与表格字段

PDF 给出的是**类别之间**的有向方位规则，例如“发动机盖 → 前侧 → 饰板”。本包整理出 12 个起点类别、61 个 PDF 部件类别、152 条方位边。12 个起点类别为：`前保险杠`、`发动机盖`、`前风挡`、`顶盖`、`后风挡`、`尾门/后备箱盖`、`后保险杠`、`翼子板`、`侧围`、`前车门`、`后车门`、`后视镜`。每条边的完整起点、终点、方位、`id` 和状态见 `schema.json` 的 `edges`；其中 150 条可供自动选择，2 条原 PDF 中可疑的“后风挡 → 前风挡”边保留但需人工复核。

`relative_position` 只能取 PDF 中的 10 种方位：`前侧`、`后侧`、`上侧`、`下侧`、`左侧`、`右侧`、`内含`、`安装侧`、`前侧/上侧`、`后侧/下侧`。它记录 **PDF 中“起点类别 → 方位 → 终点类别”这条分支的原始方位**，不是零件自身的 `location`；关系有向，不自动生成反向边。

LLM 只能为表格记录选择 PDF 允许的边，并从表格原文确定两个具体部件名称；随后再确定两端各自的物理安装位置。Gap 等七种指标及 `classification`（内部/外部）、`area` 均直接保留表格原值，不交给 LLM 重写。一个编号下连续的指标值以换行拼接在同一属性里；不同编号的 `Alignment`、`Consistent`、`Radii` 保持独立记录，不强行并入 Gap 记录。`Radii` 段按其特殊列结构读取：“区域”列是第一个部件，“编号名称”列是配合部件；章节标题不冒充物理区域。

例如表格写“机盖至散热器罩左饰板”，PDF 只提供“发动机盖 → 前侧 → 饰板”类别边。通过校验后，图中使用具体的 `:Part:发动机盖` 和 `:Part:散热器罩左饰板`，并把 `前侧` 放进两者之间的 `DTS_POSITION_RELATION.relative_position`；不会建立名为“饰板”的替代节点。

## 合并、待审与范围

一条编号记录可能因 PDF 左右方位或实际左右零件实例生成多条 DTS 关系；也可能有多个指标值但只生成一条关系。只有**起点实例、终点实例和全部关系业务属性都相同**时，重复关系才合并。输出 `graph.jsonl` 的 `source_ids` 用于追溯被合并的表格编号；Neo4j 中的关系只写上述业务属性，不写 `source_ids`。

这份 PDF 是**外形**方位图，不覆盖内部零件。内部记录、PDF 无法唯一确认的外部关系、LLM 结果校验失败、物理位置缺失的记录均进入 `review.jsonl`，不会凭空生成方位或用“未知位置”合并零件。`饰条n` 等 PDF 模板可匹配表格中的具体名称，但字面的 `n` 不作为部件节点；PDF 的“×无DTS定义”不生成边。

本文件解释 schema 的含义；需要检查某一对部件是否允许相连时，请直接查同目录的 `schema.json` 中对应 `edges`，不要仅凭本说明的例子推断新关系。
