# 汽车风格构建与归属判定技术方案

## 文档目的

本文梳理参数推荐图谱中与「汽车风格」相关的两条技术链路：

1. **美学概念实体融合**：从美学知识图谱的 `AestheticConcept(美学概念)` 中，收敛出甲方业务所需的 `汽车风格` 节点；
2. **汽车实例风格归属**：用 **LLM as Rubrics（大模型按打分表评审）**，基于双图谱证据判断每辆车属于哪些汽车风格，并写入 `EXPRESSES_STYLE`。

本文聚焦：Rubrics 是什么、为什么采用、如何降偏差对齐、以及这样做的好处。

---

## 0. 总览

```text
美学知识图谱                         汽车参数知识图谱
AestheticConcept                     汽车实例 ─[包含]→ 车身/灯光/底盘/智驾…
        │                                      │
        │ ① 实体融合                            │
        ▼                                      │
   汽车风格（主风格）                            │
        │                                      │
        └─[Guides]→ DesignParameter             │
                 │                             │
                 └──── 固化为 Style Rubric ─────┤
                                               │
                                               ▼
                                    ② LLM as Rubrics
                                               │
                                               ▼
                         汽车实例 ─[EXPRESSES_STYLE]→ 汽车风格
                              (score / confidence / evidence)
```

两条链路职责不同：


| 链路             | 解决的问题                  | 输出                             |
| -------------- | ---------------------- | ------------------------------ |
| 实体融合           | 「业务要的汽车风格」在美学图谱里对应哪些概念 | 少量 `汽车风格` 节点 + 其 `Guides→设计参数` |
| LLM as Rubrics | 「这辆具体的车」是否体现某个汽车风格     | `EXPRESSES_STYLE` 关系及可审计证据     |

## 1. 美学概念 → 汽车风格（实体融合）



### 1.1 业务目标

甲方需要的是可直接用于推荐的**汽车风格**（如科技、运动、豪华、硬派越野、简约、商务、复古等），而不是美学图谱中成百上千个细粒度 `AestheticConcept`。

因此需要：

- 从已有美学概念中**选出/收敛**业务主风格；
- 同义、近义、子类型概念**融合**到对应主风格；
- 按业务意见处理重名（如多个「运动」取连接更丰富者）、补齐缺失风格（如复古、溜背）；
- **不相关**的美学概念保留原状，不强行并入主风格。



### 1.2 融合技术方式

采用「**业务锚定 + 图谱证据 + LLM 融合评审 + 规则落图**」的四步法。

#### Step A：业务锚定主风格清单

由甲方确认主风格集合（白名单），例如：

```text
科技、运动、豪华、硬派越野、简约、商务、复古、（溜背等按意见增补）
```

每个主风格先给出**业务定义**（一句话气质边界），作为后续融合的唯一合法靶点。不允许模型自创主风格名称。

#### Step B：从图谱抽取候选证据

对每个原始 `AestheticConcept` 收集可审计上下文：

- 概念名称、描述、别名；
- 已有出边：`AestheticConcept ─[Guides(指导)]→ DesignParameter` 及 `how_to_guide`；
- 节点度数 / 连接规模（用于同名冲突消歧，例如多个「运动」优先保留连接更丰富者）。



#### Step C：LLM 做「可否融合」评审（实体对齐，不是宽松分类）

对每个原始概念提问（结构化输出）：

```json
{
  "concept_id": "...",
  "can_merge": true,
  "target_style": "运动",
  "confidence": 0.86,
  "reason": "……"
}
```

硬约束建议：

1. 这是**实体融合**，不是“沾边就算”。只有原概念本质上就是该主风格或其明确子类型时才 `can_merge=true`；
2. 安全、舒适、气动、人机、制造、法规等功能/工程概念，即使会影响某种风格表达，也**不得**因此强行并入；
3. 每个原概念最多融合到一个主风格；多义、过窄、证据不足则保留原概念；
4. `confidence` 低于门槛（如 0.80）时，按不融合处理。



#### Step D：规则落图

程序侧完成：

1. 按 `target_style` 聚合，生成/更新 `汽车风格` 节点；
2. 记录 `mergedConceptNames / mergedConceptIds`，保证可追溯；
3. 合并指向设计参数的 `Guides` 边，形成该风格的参数指导集合；
4. 同名冲突：保留连接更丰富、业务定义更贴合的节点，其余映射到保留节点；
5. 业务要求新增但图谱缺失的风格（如复古、溜背）：新建风格节点，并尽量从近义概念或后续人工补边充实 `Guides`。



### 1.3 融合结果的业务含义

融合完成后，每个 `汽车风格` 不再只是一个标签名，而是带有：

```text
汽车风格 ─[Guides(指导)]→ DesignParameter(设计参数)
```

这组关系构成下一节 Rubrics 的**领域标准来源**：某种风格在造型/工程上通常由哪些设计参数表达、如何指导。

## 2. 事情二：汽车实例 → 汽车风格（LLM as Rubrics）



### 2.1 LLM as Rubrics 是什么

**LLM as Rubrics（也称 Rubric-based LLM-as-a-Judge）** 是一种用大模型做评审的方法，核心不是“让模型凭感觉打分”，而是：

1. **先给定公开、固定的打分表（Rubric）**：写清评价维度、档位含义、通过/不通过条件；
2. **再把待评对象与证据输入模型**；
3. **要求模型先给出可核对理由，再给出分数/标签**（结构化输出）；
4. **用程序门禁与一致性机制约束结果**，而不是接受一次性自由生成。

行业上，G-Eval、Prometheus、CheckEval、以及 Langfuse / DeepEval 等评测栈，都强调：**Criteria/Rubric → Reasoning → Score**，而不是裸问“好不好/像不像”。

与「随意让模型分类」的区别：


|       | 裸问 LLM | LLM as Rubrics                |
| ----- | ------ | ----------------------------- |
| 标准从哪来 | 模型内部印象 | 事先固化的打分表（本项目来自 KG）            |
| 输出    | 常只有标签  | score + confidence + evidence |
| 可审计性  | 弱      | 强（可对照标准与证据抽检）                 |
| 业务可控性 | 难调     | 可调门槛、可改 Rubric、可做人机对齐         |




### 2.2 我们为什么采用 LLM as Rubrics

本项目要回答的不是“文本上谁和谁像”，而是：

> **在已有双图谱约束下，这辆车的真实配置/参数，是否足以支撑某个汽车风格的设计表达？**

已有 KG 能提供的关键依据恰好构成一张天然打分表：

#### （1）风格侧：什么参数影响该风格

```text
汽车风格 ─[Guides]→ DesignParameter
```

可抽出每种风格的判定标准，例如：

- 运动：车身姿态、风挡倾角、轮距、前后悬比例、动力重量比……
- 硬派越野：离地间隙、接近角/离去角、通过角、悬架行程……
- 科技：中控屏尺寸、传感器集成、ADAS/算力、HMI 响应……
- 豪华：轴距与比例、NVH、内饰材质与表面工艺……

这些不是模型临时编的“运动定义”，而是美学图谱中已经沉淀的**风格→设计参数指导关系**。

#### （2）车辆侧：这辆车实际挂了什么

```text
汽车实例 ─[包含]→ 车身 / 灯光 / 底盘 / 智驾 / 内外饰配置 …
```

汽车实例上挂接了大量零件、车身尺寸、配置与参数值，构成待评的**事实证据**。

#### （3）为什么需要“打分表评审”，而不是规则或向量单独解决

- **纯规则**：字段名异构（离地间隙 / ground_clearance / 空载最小离地间隙）、单位不一、缺字段常见，规则爆炸且脆弱；
- **纯向量相似度**：回答的是“文本近邻”，不是“设计参数是否支撑该风格”；也难以产出可给业务核对的参数级证据；
- **LLM as Rubrics**：用 KG 固化“评什么”，用 LLM 做“跨字段语义对齐与综合衡量”，再用门禁保证“必须引用图谱证据”。

因此，本方案的定位是：

> **KG 提供标准与证据，LLM 按 Rubric 做证据对齐评审；模型不负责发明风格定义，也不负责编造参数清单。**



### 2.3 本项目中的 Rubric 形态

对每种汽车风格，Rubric 由程序从融合后的美学子图自动生成，示意如下：

```text
【风格：运动】
判定目标：汽车实例是否充分体现运动风格的设计表达
评分标尺：
  0.0–0.2  几乎无关 / 证据牵强
  0.3–0.4  弱相关，偶发或次要特征
  0.5–0.6  明确相关，具备常见辅助证据
  0.7–0.8  强相关，具备主要造型/工程抓手
  0.9–1.0  近乎决定性，缺少则很难成立该风格
必须对照的设计参数（来自 Guides）：
  - Windshield Rake Angle（范围/单位/指导说明）
  - 车身姿态 Stance
  - …
车辆证据（来自该实例包含边）：
  - 车身.长宽高/轴距/离地间隙/...
  - 底盘转向 / 发动机 / 屏幕系统 / …
输出：style, score, confidence, evidence
```

模型只输出风格判定；`EXPRESSES_STYLE.parameters`（该风格对应的设计参数名列表）由程序按风格从 KG 回填，避免模型幻觉参数名。

### 2.4 单次评审流程（基础版）

```text
输入：
  - style_criteria（七种/多种主风格的固定 Rubric）
  - vehicle_context（该汽车实例及其包含尾节点属性）

LLM：
  - 将车辆属性与各风格 DesignParameter / Guides 做语义匹配
  - 仅在有明确图谱证据时输出该风格
  - 输出 score、confidence、evidence

程序门禁：
  - style ∈ 主风格白名单
  - score、confidence ≥ 业务门槛（如 0.65）
  - evidence 必须引用输入中的尾节点属性
  - evidence 必须逐字引用该风格自身的 DesignParameter 名
  - 禁止输出 parameters（由程序补齐）
```

补充约束（降低常见误判）：

- 品牌名、售价、能源类型不能单独决定风格；
- 「有运动模式」≠ 运动风格；「有中控屏」≠ 科技风格；「是 SUV」≠ 硬派越野；
- 原则上每个风格至少两条相互独立的图谱证据。

## 3. 减少偏差与对齐：Self-Consistency 与多模型共识

单次 LLM 评审仍可能受模型偏好、提示敏感度、样本顺序等影响。为提升稳定性与可辩护性，在强模型阶段采用 **Self-Consistency（自一致性）+ 多模型共识**。

### 3.1 目标

- 降低单个模型的系统性偏差（例如某模型偏爱把现代车都打成“科技”）；
- 降低同模型随机波动（温度、解码造成的分数抖动）；
- 让最终写入图谱的关系，尽量来自**可重复的共识**，而不是单次生成。



### 3.2 具体操作（建议落地）



#### 方案：3 个强闭源模型 × 各 1 次独立评审（主推）

选用能力接近的 3 个强闭源模型，例如：

```text
Model A：GPT 系列强模型
Model B：Claude 系列强模型
Model C：Gemini / 其他同级闭源强模型
```

对同一辆车、同一份 `style_criteria + vehicle_context`：

1. **独立调用 3 次**（提示词、Rubric、门禁规则保持一致；温度偏低，如 0.1–0.3）；
2. 每次得到候选风格集合：`{(style, score, confidence, evidence)}`；
3. 按风格维度做共识聚合（见下）。

> 若预算允许，也可升级为「3 模型 × 各 2 次」；首版建议先做 3 模型各 1 次，性价比更高。



#### 可选增强：同模型 Self-Consistency

对同一模型用不同随机种子/轻微温度再跑 2–3 次，先在模型内部取稳，再参与跨模型投票。适用于某模型波动大、或需要对齐分数分布时。

### 3.3 共识如何处理

对每个候选风格 `s`：


| 步骤             | 规则                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------- |
| 1. 出席投票        | 仅统计通过单次门禁（score/confidence ≥ 门槛，且 evidence 合规）的输出                                            |
| 2. 多数通过        | `s` 至少被 **2/3** 个模型输出，才允许进入最终结果                                                              |
| 3. 分数聚合        | `final_score = median(score_A, score_B, score_C)`（缺席者不参与）                                    |
| 4. 置信度聚合       | `final_confidence = median(confidence) × agreement_rate`，其中 `agreement_rate = 支持该风格的模型数 / 3` |
| 5. evidence 选择 | 优先选引用参数名最多、且字段值可在 `vehicle_context` 中逐字核对的那条；必要时拼接 2 条不重复证据                                  |
| 6. 冲突处理        | 若仅 1/3 支持，则丢弃；若 2/3 支持但分数中位数仍低于写图门槛，则不写边                                                     |
| 7. 写图          | 仅写入通过共识的 `EXPRESSES_STYLE`；`parameters` 仍由程序按风格从 KG 回填                                       |


伪代码示意：

```text
for vehicle in vehicles:
  results = [judge(model_i, rubric, vehicle) for model_i in {A,B,C}]
  for style in MAIN_STYLES:
    votes = [r for r in results if style in r and pass_gate(r[style])]
    if len(votes) < 2:
      continue
    final_score = median([v.score for v in votes])
    agreement = len(votes) / 3
    final_conf = median([v.confidence for v in votes]) * agreement
    if final_score >= T and final_conf >= T:
      write EXPRESSES_STYLE(vehicle, style, final_score, final_conf, pick_evidence(votes))
```



### 3.4 与人工对齐（建议同步做）

Self-Consistency 解决的是**模型间稳定性**；要解决“是否符合业务审美/产品口径”，仍需小样本人工校准：

1. 抽取覆盖各风格、负样本与边界样本的 gold set（建议每风格至少数十辆量级起步）；
2. 对比共识结果与人工标签，调：
  - 写图门槛 `T`；
  - Rubric 中过宽/过窄的 DesignParameter；
  - 特殊误判规则（如科技高覆盖问题）；
3. 将校准后的门槛与 Rubric 版本固化，保证可复现。

## 4. 这样做的好处



### 4.1 判断有基于 KG 的依据

- **评什么**：来自 `汽车风格 ─[Guides]→ DesignParameter`；
- **凭什么**：来自 `汽车实例 ─[包含]→ 配置/参数`；
- 模型和向量都不重新定义业务风格，只在图谱标准上做对齐。



### 4.2 可解释、可抽检

每条 `EXPRESSES_STYLE` 可追溯到：

- 命中了哪些设计参数标准；
- 车上哪些字段/取值构成证据；
- （若启用多模型）多少模型达成一致。

这比“embedding 余弦相似度 = 0.78”更适合对设计/产品同事讲清楚。

### 4.3 业务可控

- 改主风格清单、改 Guides、改门槛，即可重跑受影响实例；
- 不需要把风格判定逻辑写死成海量 if-else；
- 参数清单由程序回填，避免模型编造字段污染图谱。



### 4.4 比纯向量更贴合下游推荐任务

下游要的是：

```text
输入风格 → 推荐相关设计参数及指导
输入风格 + 车型 → 经汽车实例桥接后看参数表现
```

Rubrics 路径天然保留「风格—参数—实例」因果链；向量近邻更擅长概念召回，不擅长给出参数级归属理由。

### 4.5 用共识机制直接回应“黑箱不可信”

我们承认单次生成有偏差，因此：

- 标准公开（Rubric 来自 KG）；
- 证据可核（必须引用图谱字段）；
- 结果需共识（多模型 Self-Consistency / 多数票）；
- 并可进一步用人工 gold set 校准。

可信度来自 **标准 + 证据 + 一致性 + 校准**，而不是要求业务“相信某一个模型”。

---



## 5. 两条链路的边界（避免误解）


| 不做什么                 | 原因          |
| -------------------- | ----------- |
| 不让模型自由发明主风格名         | 主风格由甲方业务锚定  |
| 不把所有美学概念强行并入主风格      | 避免污染业务风格空间  |
| 不靠品牌词/售价单独打标         | 防止广告语式误判    |
| 不让模型生成 parameters 列表 | 参数集合以美学图谱为准 |
| 不把向量相似度当作最终归属判决      | 相似度≠设计标准满足度 |


---



## 6. 一句话总结

> **先用实体融合，把美学概念收敛成甲方要的汽车风格，并保留风格对设计参数的指导关系；再用 LLM as Rubrics，把每辆车的图谱事实对照这张打分表做归属判定；最后用多强模型自一致性共识与人工校准降低偏差。**  
> 这样，风格定义在图谱里，车辆证据在图谱里，模型只负责按公开标准做可审计的证据对齐。
